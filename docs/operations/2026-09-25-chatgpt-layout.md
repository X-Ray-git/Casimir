# 2026-09-25 ChatGPT 布局适配

## 触发与证据

用户提供本地 `ChatGPT.mhtml`，要求适配新版布局。离线读取发现原有固定 ID 和
`data-testid` 不再存在。首页没有附件卡片，因此向用户索取带附件的快照；用户随后提供
`ChatGPT-file.mhtml`，确认新版附件卡片结构。原始快照不进入仓库，也不执行其中脚本。
测试 fixture 仅手工保留必要结构，文件名替换为 `sample.pdf`，不包含账户或会话内容。

## DOM 契约与修改

| 功能 | 旧版 | 两份快照中的新版 |
| --- | --- | --- |
| 表单 | `form[data-type="unified-composer"]` | `form[data-chatgpt-composer]` |
| 编辑器 | `#prompt-textarea` | 表单内 `[data-composer-markdown][contenteditable="true"][role="textbox"]` |
| 文件输入 | `#upload-files` | 随机 ID、无 accept 限制的 file input |
| 添加按钮 | `[data-testid="composer-plus-btn"]` | `[data-composer-navigation-target="add-context"]` |
| 附件卡片 | 带文件名 aria-label 的 group | 带文件名 aria-label 的 button |
| 侧边栏 | open/close-sidebar-button | aria-controls 为 app-shell-sidebar 或 browser-sidebar-popover |

表单内先出现两个图片/视频专用文件输入，不能选择第一个 file input；因此只选通用输入，
同时支持显式空 accept。上传就绪还检查添加按钮 disabled/aria-disabled 和文件输入 disabled。
附件按原名或受限的数字后缀变体匹配，且限定在表单内；上传后匹配数量必须增加。
不将移除按钮或表单外的同名内容作为成功信号（数字后缀问题详见下文）。
临时聊天已有中文 aria-label 兼容；快照不含旧新建对话入口，现有根 URL 回退继续适用。
快照不含限流弹窗，不据此扩大自动关闭范围。

快捷键、上传脚本、后台 Runtime.evaluate 两处表达式同步更新。保留旧版契约。
继续采用原有原生 File/DataTransfer/input/change 流程，不调用未公开 API，不自动发送消息。
焦点权限、配对校验、用户交互取消和断开机制不变；此任务不解决 debugger 提示横幅。
之前可选 Chrome 启动器的未提交工作与本次适配独立保留。

## 验证与限制

- `npm run check`：Manifest、语法与最终 76 项测试通过。
- 新增 LinkeDOM 开发依赖，用真实 CSS 选择器执行脱敏 fixture 回归；扩展无新增运行时依赖。
- 新增覆盖通用输入选择、动态 ID、禁止误选媒体输入、禁用按钮、附件范围与精确名称、
  新版快捷键、后台实际聚焦表达式及用户交互保护；保留全部旧版回归。
- 两份原始 MHTML 离线执行生产选择器核对，编辑器和通用上传控件均找到；带附件快照
  的文件名卡片被正确识别。临时解码 HTML 已删除，用户原始 MHTML 保留。
- 静态快照不能证明 React 已接收合成上传事件、服务器已处理文件或原生键盘已进入页面。
  需重新加载 Casimir、刷新原页面、从论文 PDF 新建分屏，检查附件显示并直接键入文字
  （不发送），同时验收 Cmd+I、Cmd+L、临时对话和自定义提示词。
- 用户实测发现同一 PDF 被添加两次，并报告 `ChatGPT did not confirm the PDF attachment`。
  这确认进入了 DOM 确认超时分支；不能据此认为实际上传失败。旧逻辑约 1.5 秒后重放
  change，可能在首次已成功时添加第二份。现取消自动重放、延长确认到约 20 秒，
  未确认时改为中性警示，并防止重复 done 消息启动第二次添加。
- 新测试覆盖卡片延迟 5 秒、永久无法确认、重复 done，均只触发一次 change。
  此阶段尚未定位卡片未识别的原因；后续第三份故障快照才揭示数字后缀差异。
  首次两份静态快照匹配不能代替真实分屏验收。
- 没有新增权限或版本号；修复按 Unreleased 记录，用户最终明确要求维护文档后提交并推送。

## 故障快照与数字后缀修正

取消重传后用户确认不再重复，但仍有 20 秒确认超时；因此不能将“不重复”视为完整验收。
用户补充 `ChatGPT-failed.mhtml`：表单和按钮结构与前两份快照一致，卡片名称为
`2609.25518(5).pdf`，而 URL 派生的上传文件名为 `2609.25518.pdf`。原先精确相等判断
无法匹配该数字后缀。这解释了卡片存在但插件未确认的现象。

现同时接受原名与扩展名前的正整数括号后缀（允许括号前一个空格），不接受任意前缀、
其他扩展名或移除按钮。上传前记录匹配卡片数量，仅在数量增加后确认本次添加，
避免已有附件造成误判。仍不重传，也不把卡片存在等同于服务器完成解析。

76 项测试通过，包括改名后的完整上传流程、既有卡片不算成功、错名/错扩展名/表单外
卡片不算成功。原始故障快照离线执行生产匹配函数通过，并验证已有卡片计数保护。

## 最终用户验收

数字后缀修正后，用户反馈：“现在看到了‘PDF 已添加’的那个弹窗了”。结合此前反馈，
本次验证完成了附件添加、避免自动重传和识别新增附件卡片的流程。
此提示表示页面卡片已识别，不表示服务器解析完成。

新版所有快捷键及原生键盘焦点未由用户逐项重新反馈，也未由 agent 独立实测；
保留既有保护与回归测试，不把附件验收扩大为所有功能的完整验收。
用户随后要求维护文档并 commit、push；此次提交只包含布局与附件修复，
可选 Chrome 启动器及其说明继续作为独立未提交工作保留。
